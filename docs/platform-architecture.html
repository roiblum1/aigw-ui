Multi-site LLM platform

One API endpoint for every model and every site. Each conversation keeps a home site, picked in proportion to capacity. A busy site hands off as few conversations as it can, chat first. Token quotas are enforced globally from the hub. Every cluster runs Envoy AI Gateway, KServe llm-d and LMCache.

One request, end to end

  1. Entry. The client resolves llm.<domain>. Avi GSLB returns any healthy site’s gateway. That only decides where the request enters.
  2. Identity. The entry gateway checks the API key and writes the tenant ID into the tenant and fairness headers, replacing anything the client sent. An unknown key gets 401.
  3. Quota check. The rate limit service checks the tenant’s bucket in the hub Redis at cost 0. A tenant over budget gets 429 here.
  4. Conversation key. The site picker takes X-Claude-Code-Session-Id, or else hashes the tenant, system prompt, tools and first user message. Those parts are the same on every turn, so every turn gets the same key.
  5. Site choice. The picker ranks the sites that serve the model by weighted rendezvous hash, drops any whose revision or max-model-len can’t take the request, and walks the ranking. The first site whose spill zone doesn’t cover this conversation wins; if every site covers it, the home site wins. Envoy gets the ranked list.
  6. Hop. Envoy sends the request over mTLS to the chosen site’s peer listener. When the home site is the entry site, the request stays in the cluster.
  7. Admit or shed. Over its limit, the peer listener answers 503 at once and the entry tries the next site in the conversation’s ranking. Retries happen only before the first response byte, so a stream is never duplicated.
  8. Inside the site. When the pool is saturated, the EPP holds the request in its queue, ordered by priority and fair between tenants, for up to 5 s, then answers 429. It then picks a replica: cache-warm replicas first unless they are too slow, then the lowest token load.
  9. Answer and metering. vLLM streams the answer with token usage. The entry gateway deducts the tokens in the hub Redis and sends one usage record through its OTel collector to the hub.

How a conversation finds its site

Two hashes of the conversation key decide the site, so every entry gateway reaches the same answer without asking anyone.

Home site
Weighted rendezvous hash over the sites that serve the model, weight = ready replicas. With 8 and 3 B200 nodes, 8 of every 11 conversations live at the bigger site. When a site gains or loses nodes, only the conversations that have to move, move.
Spill fraction
Each site’s reporter updates it every second: up 0.03 while the site queues and another site serving the model has room, down 0.01 once it stops queueing and is under about 95% busy. Most of the time it is 0.
Every site full
The conversation stays home. Moving it would add no capacity and would throw away its KV cache. The EPP’s flow control then serves by priority.
Stale reports
A report older than a few seconds means “don’t spill to this site”, never “idle”. A site that comes back ramps its weight up over a few minutes.

Inside each site

These come from the GKE Inference Gateway write-up on Vertex AI, mapped onto the endpoint picker that KServe 0.21 already deploys.

  • Calibrate the picker. Keep KServe’s default (prefix-affinity filter, then token-load scorer). Measure peakPrefillThroughput for GLM-5.3 on B200; the default is calibrated for Qwen 32B on 2×H100. Lower maxTTFTPenaltyMs from 18,000 to about 4,000 so a hot replica loses its stickiness sooner. That is the same move as Vertex’s weight change from 3:3:2 to 3:5:2.
  • Turn on flow control. When the pool is saturated (queue depth 5 or KV cache 80% by default), requests wait in the EPP, ordered by priority and shared fairly between tenants. Cap the wait at 5 s; the EPP default is 60 s.
  • Priority classes as InferenceObjectives: chat UIs 10, Claude Code 0, scheduled agent runs −10. In phase 1 every request runs at 0, because the entry strips the header. In phase 2 the picker sets it from the API key’s class.
# LLMInferenceService, every model on every site
spec:
  router:
    scheduler:
      config:
        inline:
          apiVersion: llm-d.ai/v1alpha1
          kind: EndpointPickerConfig
          featureGates: [flowControl]
          flowControl:
            defaultRequestTTL: 5s                 # EPP default is 60s
          plugins:
            - type: approx-prefix-cache-producer
            - type: inflight-load-producer
            - type: prefix-cache-affinity-filter
              parameters:
                peakPrefillThroughput: <measured>  # default is Qwen 32B on 2x H100
                maxTTFTPenaltyMs: 4000            # default 18000
            - type: token-load-scorer
          schedulingProfiles:
            - name: default
              plugins:
                - pluginRef: prefix-cache-affinity-filter
                - pluginRef: token-load-scorer
---

Rollout in two phases

Phase 1 · config only

Weighted session hash

  • Works on Envoy Gateway 1.8.5 today: zone weights become Maglev locality weights.
  • Requests without the session header are spread by weight at random.
  • A 503 retry goes to the conversation’s stable second site.
  • Limits: weights stay static until the hub re-renders them, chat without a session header isn’t sticky, and overload only moves through shed and retry.
# Backend fleet-all-sites: one zone per endpoint
spec:

Phase 2 · site picker

Rendezvous ranking with spill

  • One internal Go service per cluster with two jobs: ext-proc picker for this site’s entry traffic, and reporter for this site’s state.
  • It writes the ranked list into Envoy’s endpointOverride header (IP:port of each site’s VIP) on its own route rule. The phase 1 rule stays the default, so a picker outage falls back to the weighted hash, never to an equal split.
  • It also sets the priority header from the key’s class.
per request, at the entry site
key  = X-Claude-Code-Session-Id
       or hash(tenant, system, tools, messages[0])
rank = sites serving the model, by w_s / -ln(H1(key, s))
                                  # w_s = ready replicas
rank = rank minus sites whose revision or
       max-model-len can't take the request
for s in rank:
    pos = H2(key, s) / 2          # chat
        | 0.5 + H2(key, s) / 2    # Claude Code, agents
    if pos >= f_s:
        route to s, rest of rank as retries; stop
else:
    route to rank[0]              # all spilling: stay home

per site, every second (reporter)
f_s += 0.03  while queueing and another site has room
f_s -= 0.01  while not queueing and under ~95% busy

Under load and failure

EventWhat happens
Normal loadEvery conversation stays on its home site. Sites fill in proportion to their nodes, 8 : 3.
One site runs hotIts spill fraction rises. Chat conversations leave first, each to its own second-ranked site. Claude Code sessions leave last.
A site loses nodesPhase 2: its weight follows ready replicas, and only the conversations that must move, move. Phase 1: weights stay until the hub re-renders them; shed and retry cover the gap.
Every site fullConversations stay home. Flow control serves by priority; a request that waits 5 s gets 429.
A site or its gateway goes downHealth checks remove it from every model within about 15 s. Connect failures go to the next-ranked site at once.
The picker is downRequests fall back to the phase 1 rule, the weighted session hash.
The hub is downBudgets fail open and config stays as last delivered. Routing keeps working, because reports go site to site.
A site comes backIts weight ramps up over a few minutes, so its conversations don’t all return to a cold cache at once.

To confirm before building

  1. Fairness header. The simplest path is to have the API-key auth write the tenant ID straight into x-llm-d-inference-fairness-id and key token budgets on that same header. The serving site must trust it only from peer certificates.
  2. Endpoint override with hostname endpoints. Confirm that Envoy Gateway 1.8.5 matches the override (IP:port) against the resolved VIP addresses of the site Backend.
  3. Spill constants. The +0.03 / −0.01 per second steps and the 1 s report interval come from the simulation. Tune them on real traffic.
  4. Chat UIs. A UI that sends a stable conversation header makes chat sticky in phase 1 as well.
  5. Peer listener limit. It sheds by request count, while the real cost is tokens. Size it from vLLM’s reported concurrency at a realistic context length.
