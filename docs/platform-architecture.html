Multi-site LLM platform

One API endpoint for every model and every site. Each conversation keeps a home site, picked in proportion to capacity. A site that is full answers 503 at once, and the request is tried at another site. Token quotas are enforced globally from the hub. Every cluster runs Envoy AI Gateway, KServe llm-d and LMCache.

One request, end to end

  1. Entry. The client resolves llm.<domain>. Avi GSLB returns any healthy site’s gateway. That only decides where the request enters.
  2. Identity. The entry gateway checks the API key and writes the tenant ID into the tenant and fairness headers, replacing anything the client sent. An unknown key gets 401.
  3. Quota check. The rate limit service checks the tenant’s bucket in the hub Redis at cost 0. A tenant over budget gets 429 here.
  4. Conversation key. The entry gateway takes the session header the client sends: X-Claude-Code-Session-Id, or the conversation header of a chat UI. It is the same on every turn, so every turn gets the same key. A request without such a header has no key.
  5. Site choice. Envoy hashes the key over the sites that serve the model, each weighted by its ready capacity. The same key lands on the same site at every entry gateway, with no service to ask. A request without a key is spread over the sites by the same weights.
  6. Hop. Envoy sends the request over mTLS to the chosen site’s peer listener. When the home site is the entry site, the request stays in the cluster.
  7. Admit or shed. Over its limit, the peer listener answers 503 at once and the entry tries another site. Retries happen only before the first response byte, so a stream is never duplicated.
  8. Inside the site. When the pool is saturated, the EPP holds the request in its queue, ordered by priority and fair between tenants, for up to 5 s, then answers 429. It then picks a replica: cache-warm replicas first unless they are too slow, then the lowest token load.
  9. Answer and metering. vLLM streams the answer with token usage. The entry gateway deducts the tokens in the hub Redis and sends one usage record through its OTel collector to the hub.

How a conversation finds its site

One hash of the conversation key decides the site. Every entry gateway has the same sites and the same weights, so each reaches the same answer without asking anyone. There is no separate service that picks a site.

Home site
A weighted consistent hash over the sites that serve the model, weight = ready instances of the model × the capacity of one instance. How the model is deployed sets the capacity: a multi-node or prefill/decode deployment is one instance, and it declares a higher capacity than a single-node one. When a site gains or loses instances, most conversations keep their site.
Without a session header
The request is spread over the sites by the same weights and is not sticky. A chat UI that sends a stable conversation header gets the same stickiness as Claude Code.
A site is full
Its peer listener answers 503 before the first byte. The entry gateway then tries another site, and the next turn of the conversation goes to its home site again.
Every site full
The request ends at a site whose EPP queues it by priority. A request that waits too long gets 429.
Weights
The hub reads each site’s ready instances at every poll and writes the weights to every cluster. A weight steps by one instance per poll, so a site that comes back does not get all its conversations at once on a cold cache.

Inside each site

These come from the GKE Inference Gateway write-up on Vertex AI, mapped onto the endpoint picker that KServe 0.21 already deploys.

  • Calibrate the endpoint picker. Keep KServe’s default (prefix-affinity filter, then token-load scorer). Measure peakPrefillThroughput for GLM-5.3 on B200; the default is calibrated for Qwen 32B on 2×H100. Lower maxTTFTPenaltyMs from 18,000 to about 4,000 so a hot replica loses its stickiness sooner. That is the same move as Vertex’s weight change from 3:3:2 to 3:5:2.
  • Turn on flow control. When the pool is saturated (queue depth 5 or KV cache 80% by default), requests wait in the EPP, ordered by priority and shared fairly between tenants. Cap the wait at 5 s; the EPP default is 60 s.
  • Priority classes as InferenceObjectives: chat UIs 10, Claude Code 0, scheduled agent runs −10. Today the hub sets the class per model, not per key: the entry gateway replaces the header a client sends with standard, and with best-effort (priority −1) for a tenant whose budget is spent on a model that serves it that way.
# LLMInferenceService, every model on every site
spec:
  router:
    scheduler:
      config:
        inline:
          apiVersion: llm-d.ai/v1alpha1
          kind: EndpointPickerConfig
          featureGates: [flowControl]
          flowControl:
            defaultRequestTTL: 5s                 # EPP default is 60s
          plugins:
            - type: approx-prefix-cache-producer
            - type: inflight-load-producer
            - type: prefix-cache-affinity-filter
              parameters:
                peakPrefillThroughput: <measured>  # default is Qwen 32B on 2x H100
                maxTTFTPenaltyMs: 4000            # default 18000
            - type: token-load-scorer
          schedulingProfiles:
            - name: default
              plugins:
                - pluginRef: prefix-cache-affinity-filter
                - pluginRef: token-load-scorer
---
apiVersion: llm-d.ai/v1alpha2
kind: InferenceObjective
metadata: {name: interactive}                     # + claude-code (0), batch-agents (-10)
spec:
  priority: 10
  poolRef: {group: inference.networking.k8s.io, name: <pool>}

How it is configured

Config only · no extra service

Weighted session hash

  • Works on Envoy Gateway 1.9.1 today: zone weights become Maglev locality weights.
  • Requests without the session header are spread by weight at random.
  • A 503 is retried at another site.
  • Limits: weights change only as fast as the hub polls the clusters, chat without a session header isn’t sticky, and overload only moves through shed and retry.

Under load and failure

EventWhat happens
Normal loadEvery conversation stays on its home site. Sites fill in proportion to their nodes, 8 : 3.
One site runs hotPast its limit it answers 503, and those requests are tried at another site. Its conversations come back to it as soon as it has room.
A site loses instancesThe hub lowers the weight once two polls in a row agree; shed and retry cover the gap.
Every site fullConversations stay home. Flow control serves by priority; a request that waits 5 s gets 429.
A site or its gateway goes downHealth checks remove it from every model within about 15 s. Connect failures go to another site at once.
The hub is downBudgets fail open and config stays as last delivered. Routing keeps working: the gateways need nothing from the hub to route.
A site comes backIts weight rises one instance per hub poll, so its conversations don’t all return to a cold cache at once.

To confirm before building

  1. Fairness header. The simplest path is to have the API-key auth write the tenant ID straight into x-llm-d-inference-fairness-id and key token budgets on that same header. The serving site must trust it only from peer certificates.
  2. Chat UIs. A UI that sends a stable conversation header makes chat sticky as well.
  3. Peer listener limit. It sheds by request count, while the real cost is tokens. Size it from vLLM’s reported concurrency at a realistic context length.
