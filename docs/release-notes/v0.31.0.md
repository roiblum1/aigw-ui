# 0.31.0 (not released yet)

The hub talks to the clusters and to Postgres side by side instead of one
request after another. On a local API server with 20 models in best-effort
mode (222 objects), a sync that changes nothing took 4.6 s, against 2 min
11 s in 0.30.0, and a sync writes the tenants' token policy first, so a
revoke is in effect at its start. The usage page, the best-effort loop, the
history and the tenants' page read what all clusters have in common once.

Database: migration 034 adds three indexes: `api_keys (key_prefix)`, for a
tenant signing in with an API key, and `usage_hours (model_id)` and
`token_hours (model_id)`, for deleting a model's history.

## Upgrading

- A sync sends each cluster's API server up to 50 requests a second after a
  burst of 100 (client-go's default, used before, is 5 after 10). A
  cluster's API Priority and Fairness may queue them; client-go waits and
  retries.
- The chart requests 250m CPU (was 50m), still with no CPU limit.
- `GET /usage/history` with a `tenant_id` that is not a UUID answers 404; it
  answered an empty list.

## Changed

- **A sync writes in five stages**, each stage's objects eight at a time:
  the key `Secret`; the `SecurityPolicy` that names it; `Backend`,
  `AIServiceBackend` and the request classes; the `AIGatewayRoute`s; the `QuotaPolicy`,
  `BackendTrafficPolicy` and `EnvoyPatchPolicy` objects. A stage that fails
  stops the sync before the next. The task log lists the objects in the
  order they were rendered, as before.
- **A revoke is in effect at the start of a sync.** The token policy and the
  key Secret were written last, after every model's objects.
- **A sync does not read an object before writing it.** Each cluster's
  client remembers each object as its last sync left it (UID and
  generation); only the first sync after the server starts reads them. The
  status of an object the sync did not change comes from the answer to its
  write, and only changed objects are read again after the two seconds'
  wait. An object someone else changed in between is listed as updated
  once.
- **One client per cluster**, kept while its kubeconfig stays the same, for
  the sync, the polls and the measurements: they share its connections and
  its request rate. A client was made for each sync and poll.
- **Polls run on their own loop**, so a change never waits for a poll of all
  clusters. A poll reads the cluster's routes, the gateway's model list and
  what the cluster serves side by side, and each service's workload eight at
  a time.
- **The marks on the cluster's own routes** list each namespace's routes once
  a sync, not once per `QuotaPolicy`. The leftovers of every kind are listed
  at once.
- **The usage reads** build every cluster's state from one read of what the
  clusters have in common: about thirteen queries and one per cluster, where
  each cluster took about fifteen. Working out the counters' names took
  1.4 ms and 7.3 MB at 1,000 tenants and ten models, against 3.8 ms and
  17 MB.
- **The tenants' page** reads its usage, history and prices side by side, and
  finds the tenant's history by its UUID; compared as text, it read every
  tenant's history of the last 30 days.
- **The history** deletes the cursors of the counters that went, by key; it
  sent every cursor's key each minute.
- **Site weights are worked out again** after a change of a cluster, of a
  model's endpoints or entry route, or a drain, which lock every model to
  do it; no longer after a change of a tenant, key, quota, budget or price.
  The poll of all clusters still does it every minute.
- **The optimization guide** sizes flow control right. `maxConcurrency` of
  the `concurrency-detector` is per endpoint, each port the pool lists, so
  per rank on a data-parallel pod; the guide said per pod and named vLLM's
  `--max-num-seqs`, which on a pool of 16 rank endpoints would have let
  about 1,024 requests through before the picker held any back. It is sized from the hub's
  capacity measurement now. The guide also sets `defaultRequestTTL` (60 s
  when left out, shorter than waits already seen on the lab) and shows
  `defaultNegativePriorityBand`, as llm-d router v0.10.0 defines them, and
  says which headers a client cannot choose.
- **Code.** The public half of a signing key goes to and from a JSON Web Key
  through `crypto/ecdsa`'s encoding, without the coordinates Go 1.26
  deprecated; a coordinate that is not 32 bytes is refused. An unused helper
  and a dead assignment are gone. CI runs staticcheck v0.8.2.

## Tested

On 2026-10-17:

- `go test -race ./...` with the store and usage tests. New: the stages of a
  sync, their order and a failed stage (`TestSyncAppliesInStages`); a sync
  that remembers objects, reads nothing before its writes and tells a
  deleted object (`TestSyncRemembersObjects`); one route list per namespace
  for two priced policies; every cluster's state from one read equal to
  each cluster's own (`TestRenderStatesShareOneRead`); a JWK coordinate of
  31 bytes refused.
- `hack/test-apiserver.sh` (Envoy Gateway v1.9.2 and Envoy AI Gateway
  v1.2.0 CRDs) and its v1.9.1 / v1.1.0 variant.
- A sync of 20 fleet models in best-effort mode, each with a quota (222
  objects), into the local API server of `hack/test-apiserver.sh`:

  | | 0.30.0 | 0.31.0 |
  |---|---|---|
  | Creates everything | 2 min 9 s | 11.1 s |
  | Changes nothing | 2 min 11 s | 4.6 s, then 4.6 s again |

- `render.Counters` with the keys of 1,000 tenants on ten priced models
  (`go test -bench`): 3.8 ms, 17 MB and 70,894 allocations before; 1.4 ms,
  7.3 MB and 30,536 after.
- `go vet`, staticcheck v0.8.2, `hack/check-duplication.sh`,
  `hack/check-chart.sh`, `hack/check-release-note.sh`.

Not run:

- Anything on a real cluster: a sync's time and a revoke's on the lab, where
  the API server is further away than a local one, and 50 requests a second
  against OpenShift's API Priority and Fairness.
- The tenants' page and the usage page against the sandbox hub.
