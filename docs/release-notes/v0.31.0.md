# 0.31.0 (not released yet)

The hub talks to the clusters and to Postgres side by side instead of one
request after another. On a local API server with 20 models in best-effort
mode (222 objects), a sync that changes nothing took 4.6 s, against 2 min
11 s in 0.30.0, and a sync writes the tenants' token policy first, so a
revoke is in effect at its start. The usage page, the best-effort loop, the
history and the tenants' page read what all clusters have in common once.

Database: migration 034 adds three indexes: `api_keys (key_prefix)`, for a
tenant signing in with an API key, and `usage_hours (model_id)` and
`token_hours (model_id)`, for deleting a model's history.

## Upgrading

- A sync sends each cluster's API server up to 50 requests a second after a
  burst of 100 (client-go's default, used before, is 5 after 10). A
  cluster's API Priority and Fairness may queue them; client-go waits and
  retries.
- The chart requests 250m CPU (was 50m), still with no CPU limit.
- `GET /usage/history` with a `tenant_id` that is not a UUID answers 404; it
  answered an empty list.

## Changed

- **A sync writes in five stages**, each stage's objects eight at a time:
  the key `Secret`; the `SecurityPolicy` that names it; `Backend`,
  `AIServiceBackend` and the request classes; the `AIGatewayRoute`s; the `QuotaPolicy`,
  `BackendTrafficPolicy` and `EnvoyPatchPolicy` objects. A stage that fails
  stops the sync before the next. The task log lists the objects in the
  order they were rendered, as before.
- **A revoke is in effect at the start of a sync.** The token policy and the
  key Secret were written last, after every model's objects.
- **A sync does not read an object before writing it.** Each cluster's
  client remembers each object as its last sync left it (UID and
  generation); only the first sync after the server starts reads them. The
  status of an object the sync did not change comes from the answer to its
  write, and only changed objects are read again after the two seconds'
  wait. An object someone else changed in between is listed as updated
  once.
- **One client per cluster**, kept while its kubeconfig stays the same, for
  the sync, the polls and the measurements: they share its connections and
  its request rate. A client was made for each sync and poll.
- **Polls run on their own loop**, so a change never waits for a poll of all
  clusters. A poll reads the cluster's routes, the gateway's model list and
  what the cluster serves side by side, and each service's workload eight at
  a time.
- **The marks on the cluster's own routes** list each namespace's routes once
  a sync, not once per `QuotaPolicy`. The leftovers of every kind are listed
  at once.
- **The usage reads** build every cluster's state from one read of what the
  clusters have in common: about thirteen queries and one per cluster, where
  each cluster took about fifteen. Working out the counters' names took
  1.4 ms and 7.3 MB at 1,000 tenants and ten models, against 3.8 ms and
  17 MB.
- **The tenants' page** reads its usage, history and prices side by side, and
  finds the tenant's history by its UUID; compared as text, it read every
  tenant's history of the last 30 days.
- **The history** deletes the cursors of the counters that went, by key; it
  sent every cursor's key each minute.
- **Site weights are worked out again** after a change of a cluster, of a
  model's endpoints or entry route, or a drain, which lock every model to
  do it; no longer after a change of a tenant, key, quota, budget or price.
  The poll of all clusters still does it every minute.
- **The optimization guide** sizes flow control right. `maxConcurrency` of
  the `concurrency-detector` is per endpoint, each port the pool lists, so
  per rank on a data-parallel pod; the guide said per pod and named vLLM's
  `--max-num-seqs`, which on a pool of 16 rank endpoints would have let
  about 1,024 requests through before the picker held any back. It is sized from the hub's
  capacity measurement now. The guide also sets `defaultRequestTTL` (60 s
  when left out, shorter than waits already seen on the lab) and shows
  `defaultNegativePriorityBand`, as llm-d router v0.10.0 defines them, and
  says which headers a client cannot choose.
- **Code.** The public half of a signing key goes to and from a JSON Web Key
  through `crypto/ecdsa`'s encoding, without the coordinates Go 1.26
  deprecated; a coordinate that is not 32 bytes is refused. An unused helper
  and a dead assignment are gone. CI runs staticcheck v0.8.2.

`/release-e2e` procedure) on the sandbox hub, image `sha-15f598c6d146`
(chart 0.31.0 with the guide of #71; memory limit 1 GiB), and the lab:

**The memory fix holds.** The hub was not restarted by the platform once.
It used 45 to 79 MiB after seeding and the syncs, and moved between about
80 and 193 MiB a minute while `qwen-tiny` was in best-effort mode and the
checks ran; 95 MiB once the tenants were deleted. 0.30.0 before the fix
peaked at 868 MiB and was killed at 512 MiB; 0.29.0 used 45 MiB.

Scale (0.30.0 at `d376a65` in brackets):

- Creating the 1,000 tenants took 132.6 s (138.8 s).
- Three full syncs took 1.0 s each (10.8 s).
- A revoked personal key's token was refused 3.0 s after the revoke; the
  revoke's sync took 3.5 s (9.8 s). The self-test's revoke: 2 s after the
  sync.
- A change bound to the gateway config held 3 to 8 s after it: an amount's
  new rule 6.0 s, a disable 4.8 s and an enable 3.1 s, a pool change 4.6 and
  5.6 s, its syncs 1.5 to 6.1 s (8 to 9.5 s); a price change 14.3 s. A
  tenant's move to best-effort synced in 3.7 s (about 16 s).
- `GET /tenants` took 2.1 s and `GET /usage` 3.7 to 4.4 s just after
  seeding, then 1.34 to 1.40 s and 2.2 to 2.9 s for the rest of the run
  (1.40 s and 2.89 s); `/healthz` took 0.53 s from the test machine.
  Postgres used 125 MiB (124 MiB).

  `aigw-ui-tenant-budgets` 5 (2,238 bytes). A `max_tokens: 1` request took

- No request was throttled by the cluster's API server: the hub logged no

What held: quotas, budgets, model lists, the pool and limits in tokens;
best-effort (listed before the answer that reached 6 of 6 came back, capped
at 3 with no overshoot) and best-effort below regular tenants; the cost
formula (10 of 10); cached prices on both paths (466 credits instead of
3,922; Anthropic 476); token counts equal to the answers and the tenant's
page equal to Redis; live changes; cancelled requests as in 0.30.0; the
entry route, the retry patch, the drain refusal; a model deleted by hand
stayed deleted (the gateway listed it 7.0 s, 13.9 s before); a live
measurement and the planner's figures; spoofing; the hub at 0 for 40 s;
backend headers. In the history, a quota reset 25 s after three requests
kept them, a tenant's counters under two amounts (10 and 14) made one row
of their sum, and two budget tenants whose rule moved within the day
matched their counters.

Found:

- **The history loses a budget tenant's last use on a model when the
  budget-pass rule moves.** The rule is the model's last, so it moves with
  every amount added or removed. The history reads it at its current
  position only (`HistoryCounters`; `formerAmounts` skips budget counters),
  so use counted at the old position after the history's last look (up to a
  minute) never reaches it. A tenant sent 5 requests at 13:55 UTC under
  rule 4; seeding moved the rule seconds later; the history holds 5 of its
  10 for the day, Redis 10 (5 under rule 4, 5 under rule 9). The gateway's
  enforcement is not affected.
- A request 2.7 s after its tenant moved to best-effort got HTTP 500 in
  67 ms: the AI gateway's ext_proc answered `unknown backend
  …/fleetbe-qwen-tiny/route/fleetbe-qwen-tiny/rule/0/ref/0` while Envoy
  already had the new route. The next request was answered. With 0.30.0's
  16 s sync no request fell in that gap.
- The scheduler at 0 gave HTTP 503 (the peer hop's 503, retried by the
  entry route until `URX`), where 0.30.0 saw 500; answered again 5 s after
  it was back. The scheduler ran the round-robin config below then.
- With `round-robin-fairness-policy` on the band of priority 0 and
  `defaultRequestTTL: 300s` on `qwen-tiny`'s scheduler for the run (at the
  user's request; put back afterwards), one tenant's single request was the
  first one served from the queue (25.9 and 14.7 s, against 44.1 and
  28.0 s with the default fairness, behind another tenant's six), and the
  sync's warning went away. `maxConcurrency: 2` was kept: the pool has one
  endpoint.
- As in 0.30.0: lowering an own quota from 14 to 6 after 8 let the tenant
  use 20 in the hour; a cancel before the first token, or of a request
  without streaming, is charged nothing.
- The first sync after the hub starts waits for the 5-minute resync; no
  change was pending.

Not run:

- 50 requests a second against OpenShift's API Priority and Fairness with
  many clusters or objects: the lab is one cluster with 16 to 22 objects.
- Envoy Gateway's `XDSNameSchemeV2` flag (skipped at the user's request);
  cache hits steered between replicas, and what needs a second site.
- A pool window change from 1h to 1d: the day's counter was already spent
  by the 0.30.0 run earlier that day, so it says nothing.
- The tenants' page and the usage page in a browser (the APIs were timed).
