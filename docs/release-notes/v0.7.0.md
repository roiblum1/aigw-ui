# 0.7.0 (2026-10-09)

## New

- **Site weights.** The hub now reads from every cluster how many instances
  of each model are ready, and keeps the gateways' zone weights in line with
  it, so each site gets conversations in proportion to what it can serve.

  The weight of a site for a model is **ready instances × capacity of one
  instance**:
  - *Ready instances* comes from each `LLMInferenceService`'s status. A
    multi-node instance counts once. With separate prefill and decode, only
    complete instances count.
  - *Capacity of one instance* is declared, because it depends on how the
    model is deployed: a multi-node prefill/decode instance is one instance
    but can be worth several single-node ones. Set it with the annotation
    `aigw-ui.io/capacity-per-instance` on the `LLMInferenceService`, in any
    unit that is the same for the model everywhere, such as tokens per second
    from your benchmark job. Without it, an instance counts as 1.

  The weight follows the ready capacity carefully: it rises by one instance
  per poll, drops only after two polls in a row agree, and stays as it is
  when a cluster cannot be asked.
- **Fleet clusters.** A cluster takes part in site weights once *Part of the
  fleet* is ticked on it. Every fleet cluster is a zone in every model's
  weights, with 0 where it does not serve the model, and only fleet clusters
  get the weights written. A fleet cluster must enforce API keys: without
  that a client could name another tenant and spend its quota at any site.
- **Drain and undrain.** *Drain* on the Models page takes one site out for
  one model before maintenance: its weight steps down to 0, one instance per
  poll, and stays there. *Undrain* brings it back the same way. Draining the
  last site with capacity is refused.
- **Recipe warnings.** The Models page warns when the sites that serve a
  model declare different `aigw-ui.io/model-revision` or
  `aigw-ui.io/max-model-len` on their `LLMInferenceService`s.
- **Client listener.** A cluster can name the Gateway listener clients come
  in on. The API-key policy then attaches to that listener alone, so a
  listener that other sites forward to is not asked for a key the entry
  gateway has already removed.
- **GitHub workflow** (`.github/workflows/ci.yml`). Every pull request and
  push runs the unit tests, the tests against a real Kubernetes API server
  (`hack/test-apiserver.sh`), the UI build and a chart lint. A push to `main`
  also pushes the image to `ghcr.io/roiblum1/aigw-ui` as `main` and
  `sha-<commit>`. A tag `v1.2.3` pushes `1.2.3` and `latest` and publishes a
  GitHub release with `docs/release-notes/v1.2.3.md` as its text. Every run
  fails when the version in the chart has no release note.
- **Weights on the Models page.** Each cluster a model is served from shows
  its weight and its share of the model's traffic. `GET /api/v1/models`
  returns the same as `capacity` per endpoint and `site_weights` per model.
- **Activity shows weight changes**, with the policies that were updated on
  each cluster.
- **The Architecture page now describes weights the same way**: ready
  instances times the capacity of one instance, in place of ready nodes. Its
  policy example shows the label and annotation this tool looks for.

## What you have to do to use it

Nothing changes until a cluster is in the fleet and its chart asks for
weights. Tick *Part of the fleet* on each site's cluster, then for each model:

1. On the model's `BackendTrafficPolicy`, set the label
   `aigw-ui.io/zone-weights: "true"` and the annotation
   `aigw-ui.io/model: <model name>`, and do not set `weightedZones` in the
   chart. The policy can be in any namespace.
2. Give each endpoint of the cross-site `Backend` a `zone` equal to the
   cluster's name in this tool, for example `ocp4-prod-llm-site1-a`.
3. Tell Argo CD to ignore the one field this tool writes:

   ```yaml
   spec:
     ignoreDifferences:
       - group: gateway.envoyproxy.io
         kind: BackendTrafficPolicy
         managedFieldsManagers: [aigw-ui-weights]
     syncPolicy:
       syncOptions: [RespectIgnoreDifferences=true]
   ```

4. Where a model is deployed in different ways on different sites, set
   `aigw-ui.io/capacity-per-instance` on each `LLMInferenceService`.
   `aigw-ui.io/capacity-per-replica` is read too when the first is not set.
5. On a gateway with a listener for other sites, set the cluster's *Client
   listener* to the name of the client one, for example `https`.

The policy stays yours. This tool writes only
`spec.loadBalancer.zoneAware.weightedZones`, and never creates or deletes the
policy.

## Limits you should know

- **The capacity number is only as good as your benchmark.** With different
  deployments of one model and no annotation, every instance counts as 1 and
  the stronger site gets too little.
- **A weight moves every conversation that hashed to the lost share.** The
  step rules keep that rare, not free.
- **During a ramp, Activity gets one task per step.** A site that comes back
  with 8 instances produces 8 tasks over 8 polls.
- **The hub sets the weights, the gateways keep them.** With the hub down the
  last weights stay.
- **Weights are not written for a model while any site that serves it has
  never reported a capacity.** The Models page says which.
- **A drain starts on the next poll**, not at once, and the gateways get each
  step a few seconds after the poll.
- **A cluster serves a model only if it has an `LLMInferenceService` for
  it.** A fleet cluster that serves a model some other way gets weight 0.
- **Not in this release, from the hub guide:** the hub does not yet render
  the per-model entry route, the shared all-sites `Backend` or the full
  `BackendTrafficPolicy`; the charts still own them. Also not built: picking
  the newest served API version, fleet revision, certificate and entry
  checks, EPP config comparison, and the extra self-test steps.

## Upgrade

```sh
helm upgrade aigw-ui deploy/chart/aigw-ui -n aigw-ui
```

Two migrations, `008_site_capacity.sql` and `009_fleet.sql`, add columns. The kubeconfig of each
cluster must be able to list `llminferenceservices.serving.kserve.io` in all
namespaces, and to list and patch `backendtrafficpolicies`. A cluster-admin
kubeconfig already can. A cluster without KServe is skipped without an error.

## What was tested, and what was not

Tested here:

- Unit tests for the step rules, the weights and the instance count,
  including prefill/decode.
- Against a Kubernetes 1.37 API server with cut-down CRDs
  (`internal/kube/testdata/weights-crds.yaml`):
  - the capacity read from `LLMInferenceService` objects in the shapes KServe
    0.21's source produces;
  - that this tool and another field manager, standing in for Argo CD, can
    each apply to the same policy without undoing the other, and that a site
    that stops serving a model loses its zone.
- Three simulated fleet sites, one without the model: it got weight 0 in the
  policy; a drain stepped one site down one instance per poll and draining
  the other was refused; the key policy carried `sectionName: https`.
- The whole loop on two simulated sites: a drop applied on the second poll, a
  rise of one instance per poll, a capacity of 2.5 per instance, and the same
  weights on both sites.

**Not tested: a real KServe, a real Envoy Gateway, or Argo CD.** The field
paths come from reading the KServe 0.21 and Envoy Gateway 1.8.5 sources.

| # | What is assumed | How to check |
|---|---|---|
| 20 | KServe fills `status.workloads.primary.readyReplicas`, and `prefill.readyReplicas` for separate prefill | `oc get llminferenceservice <name> -o jsonpath='{.status.workloads}'`. The Models page must show a weight tag for the model |
| 21 | For a multi-node deployment the count is ready groups, one per instance | Compare the tag's tooltip with `oc get leaderworkerset` |
| 22 | A stopped service carries `serving.kserve.io/stop: "true"` | Stop one and check that its weight goes to 0 after two polls instead of staying |
| 23 | Envoy Gateway accepts a zone weight of 0 and sends that zone nothing | Scale one site's model to zero in a test and watch the policy's status and the traffic |
| 24 | Argo CD leaves `weightedZones` alone with `ignoreDifferences` on the field manager | After a weight change, the application must stay Synced and the weights must survive an Argo sync |
| 25 | The zone on the `Backend` endpoints matches the cluster names here | Compare `oc get backend -o yaml` with the Clusters page |
