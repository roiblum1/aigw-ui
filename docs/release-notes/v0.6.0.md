# 0.6.0 (2026-10-08)

## New

- **Self-test.** A new button on each cluster checks, with real requests
  through that cluster's gateway, that the objects this tool applies do what
  they are meant to. It adds a temporary tenant with a key and a quota of
  1 token per hour, and then checks in order that:
  1. the gateway lists the model;
  2. the cluster and the gateway's controller accept the objects;
  3. a request with the new key is answered;
  4. a request with an unknown key is refused;
  5. the tokens show up in Redis under the counter name the Usage page uses;
  6. the next request is refused with 429;
  7. after a usage reset the tenant is answered again;
  8. the temporary tenant is gone.

  It takes about a minute and a handful of one-token requests. The result is
  shown step by step and written to Activity. Over the API:
  `POST` and `GET /api/v1/clusters/{id}/selftest`. The cluster needs a
  Gateway URL.
- **Audit log.** Activity has a second tab that lists every request that
  changed something or tried to: when, who, what, the result and where it came
  from. Over the API: `GET /api/v1/audit`. Every entry is also written to the
  server log, so a log collector can keep it for longer than the 20,000
  entries the table holds.
- **A name at sign-in.** The sign-in page asks for an optional name, which is
  recorded in the audit log. API callers send it in the `X-On-Behalf-Of`
  header. See the limits below.

## Fixes

- **A tenant's usage no longer restarts when another tenant's quota is added
  or removed.** The position of a tenant's rule in the `QuotaPolicy` is part
  of the name of its counter in Redis. Rules were ordered by tenant name, so a
  new quota moved every tenant after it to a new counter, and their usage in
  the current window started again from zero. A quota now keeps its position
  for as long as it exists. A removed quota leaves a placeholder rule that
  matches no request, and the next new quota on that model takes its place.
- **Removing a cluster is now in the task log.** It was the one change that
  left no trace.

## Limits you should know

- **The audit log does not prove who someone is.** There is still one shared
  admin token. The name is whatever the browser or the API caller sends.
  A verified identity needs real login, which is not built yet.
- **Requests with a wrong token are not in the audit log.** They are written
  to the server log as `request with a wrong token`.
- **The pool's counter can still restart.** It is named after the number of
  rules, so it starts again for the current window when a quota is added at
  the end of a model's list or the last one is removed. The self-test does
  both. This only matters for a model with a large shared pool.
- **The self-test touches production objects.** It rewrites the model's
  `QuotaPolicy` and the key `Secret` on the tested cluster twice. Other
  tenants' rules and counters are not changed.
- **Self-test results are kept in memory.** After a restart the modal is
  empty; the outcome is still in Activity.

## Upgrade

```sh
helm upgrade aigw-ui deploy/chart/aigw-ui -n aigw-ui
```

Two migrations run at start: `006_quota_slots.sql` gives every existing quota
the position it is rendered at today, and `007_audit_log.sql` adds the audit
table. The objects on the clusters come out the same after the upgrade, so no
counter restarts because of it.

One case does change: a quota of a **disabled** tenant used to take no
position. If you have disabled tenants with quotas, enabling one later puts it
after the others instead of in name order, which no longer moves anyone.

Tenant slugs starting with `selftest-` are now refused. An existing tenant
with such a slug would be deleted by the first self-test: rename it first by
recreating it under another slug.

## What was tested, and what was not

Tested here:

- The unit tests, including new ones for rule positions and counter names.
- The upgrade on a database with existing quotas: the manifests before and
  after were identical.
- The self-test from start to finish against a stand-in gateway written for
  this purpose, which enforces the applied `QuotaPolicy` and counts in a real
  Redis: all eight steps, the "pool still has tokens" case, and cleanup.
- The audit log in the UI and over the API, including a non-ASCII name.

**Not tested: the self-test against a real Envoy AI Gateway.** The stand-in
follows the same reading of the gateway's source as the rest of this tool, so
it cannot find a mistake in that reading. The self-test exists to find such
mistakes on your gateway. Its first real run is the test.

### Which open items the self-test checks

The numbers refer to the tables in [0.4.0](v0.4.0.md) and [0.5.5](v0.5.5.md).

| # | Item | Self-test step that checks it |
|---|---|---|
| 1 | Counter names in Redis | 5 |
| 3 | Deleting a counter resets usage | 7 |
| 4 | A reset frees a tenant that is being refused | 7 |
| 5 | The controller sets `Accepted` within two seconds | 2 shows the verdict it found |
| 7 | The client ID is forwarded in `x-aigw-client-id` | 3 and 5 |
| 8 | A regular-expression selector matches the tenant's keys | 3 and 5, with one key |
| 10 | A quota works on a backend without `modelNameOverride` | 5 and 6, when run on such a model |
| 11 | `/v1/models` answers with "Enforce API keys" on | 1 |
| 16 | A tenant over its quota draws from the shared pool | 6 reports "Unclear" with the pool's balance when this happens |

Still to check by hand: one counter across two sites (9), the finalizer error
(12), dry-run quotas next to the pool (13), cost expressions (14), and the
pool's counter name (15).
