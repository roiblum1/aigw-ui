# 0.4.0 (2026-10-08)

## New

- **Live usage per tenant.** A new **Usage** page shows, for every tenant
  quota, the tokens used in the current window, the limit, and when the
  window resets. It refreshes every 5 seconds. The same bar appears next to
  each quota on a tenant's page, and the data is available from
  `GET /api/v1/usage`.

  The numbers are read from the counters that the gateways' quota rate limit
  services keep in the shared Redis, so they are exactly what is enforced.
  The server only reads from Redis.

- **Reset usage.** With `redis.allowReset` on, an admin can set a tenant's
  usage on one model back to zero for the rest of the current window. The
  limit stays as it is. Available as a button on the Usage page and on the
  tenant's page, and as `POST /api/v1/tenants/{id}/quotas/{model_id}/reset`.
  Every reset is written to the server log. It is off by default, so Redis
  stays read-only unless you turn it on.

- **Task log.** A new **Activity** page lists every change (adding a
  tenant, creating or revoking a key, setting a quota, switching to dry run,
  resetting usage, changing a model or cluster) and shows, per cluster, what
  the sync did: each object the cluster confirmed as created, updated or
  deleted, and whether the gateway's controller accepted it. A cluster that
  could not be synced shows as Failed and is retried. Also available from
  `GET /api/v1/tasks`, so a portal can check that its request was applied.

## Setup

Usage monitoring is off until the server is told where Redis is:

```sh
helm upgrade aigw-ui deploy/chart/aigw-ui -n aigw-ui \
  --set redis.url='rediss://:<password>@<redis route host>:443' \
  --set redis.caConfigMap=<configmap with ca.crt>
```

- For Redis behind an OpenShift Route, use `rediss://` and port 443. A Route
  only carries TLS, so Redis must serve TLS itself and the Route must use
  passthrough termination.
- For Redis reached through its Service, use `redis://<service>.<namespace>.svc:6379`.
- To keep the password out of the Helm values, put the URL in a Secret under
  the key `url` and set `redis.existingSecret`.

## Good to know

- Each sync now reads every object before applying it and reads the AI
  gateway objects' status afterwards. That is roughly twice the API calls
  per sync, and a sync that changed something takes two seconds longer.
- Migration `005_tasks.sql` adds the task tables. It runs on startup.

- A reset applies on every site that shares the counter. A tenant that had
  already reached the limit can stay blocked for a while afterwards if the
  rate limit service caches over-limit keys (`LOCAL_CACHE_SIZE_IN_BYTES`).

- Only the current window is shown. There is no usage history.
- Clusters share a counter only when the model's `AIServiceBackend` has the
  same namespace and name on each of them. The page warns when it finds
  separate counters, because the tenant then gets the limit once per cluster.
- Adding or removing a tenant quota on a model restarts the current-window
  counters of the tenants that sort after it. The gateway names a counter
  after the rule's position in the policy.

## Not verified: check these before relying on this release

None of this release was run against a real Envoy AI Gateway or your Redis.
The usage and reset features were tested against a local Redis with counters
written by hand, and the task log against a stand-in for the cluster API.
Each item below says what was assumed and how to check it.

### New in this release

| # | What is assumed | How to check | If it is wrong |
|---|---|---|---|
| 1 | The counter names in Redis match the ones the server computes. They were derived from the gateway's and the rate limit service's source code | Send a few requests as a tenant that has a quota, then open **Usage**. The bar must move | The page shows a warning with a real key from Redis next to the expected one. Send both to fix the format. If only the start differs, set `redis.keyPrefix` |
| 2 | Redis can be reached through the OpenShift Route with `rediss://<route host>:443`. **Verified on OpenShift 4.20** with a TLS Redis, a passthrough Route and a private CA in `redis.caConfigMap`: reading and resetting a counter both worked | Set `redis.url` and open **Usage**. An error banner means it cannot connect | Check that Redis serves TLS, that the Route uses passthrough, and that `redis.caConfigMap` holds the right CA. Or use the Service address instead |
| 3 | Deleting a counter resets usage, and the next request is counted from zero | Press **Reset usage**, send one request, and check that the bar restarts from that request | The API answer shows `"deleted": 0` if no counter was found, which points back to item 1 |
| 4 | A reset frees a tenant the gateway is already rejecting. This holds only when the rate limit service has no local over-limit cache | Run `oc get deploy -A -o yaml \| grep -A1 LOCAL_CACHE_SIZE_IN_BYTES`. No output means the cache is off | With the cache on, a tenant at the limit stays rejected until the window ends, whatever is in Redis |
| 5 | The gateway's controller sets a condition named `Accepted` or `NotAccepted` on its objects within two seconds | Set a quota and open the task in **Activity**. The `QuotaPolicy` line should end with `gateway: Accepted` | With a slower controller the line shows no verdict, or the verdict on the previous version. The object is still applied |
| 6 | An apply that changes nothing does not move an object's generation, so it is not listed as "updated" | Press **Sync** twice in a row. The second task should say "Nothing had to change" | Unchanged objects show up as "updated" on every sync. This is noise, not a fault |
