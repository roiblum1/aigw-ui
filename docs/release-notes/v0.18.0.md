# 0.18.0 (not released yet)

The hub issues tokens: a new key is a JSON Web Token the hub signs, which
the client pastes as its API key and every gateway checks against the hub's
public keys. Step 5a of the
[design](../design/capacity-prices-wallets.md#identity-and-quota-rules).

Database: migration 021 adds `signing_keys`, the kind, `jti`, signing key
and expiry of a key, and `token_denials`, which a trigger on `api_keys`
fills when a token is revoked or its tenant deleted.

## Upgrading

Nothing changes on the gateways until the first token is created. Then:

- **Every gateway takes API keys and tokens**, at the next sync of each
  cluster. The SecurityPolicy `aigw-ui-api-key-auth` gains a JWT check after
  the API key check, the Secret lists every token beside the API keys, and
  the API key check no longer removes the credential: the backends the hub
  renders remove `Authorization` and `x-api-key` instead. A route of the
  cluster's own passes the credential on to the model server.
- **Once the last API key is revoked**, the gateways take tokens only, list
  no key, and the Secret `aigw-ui-api-keys` is removed.
- **Nothing a tenant may spend changes**: a token's client ID has the API
  key's form, so the per-tenant rules count its requests as they did.

To move a tenant: create a token for it, let it switch its clients, then
revoke its API keys. Running the self-test does not create the first token:
its tenant gets an API key until the hub has issued one.

Set `tokens.issuer` and `tokens.audience` before the first token if the
defaults (`aigw-ui`, `aigw-fleet`) do not suit you: changing them later
refuses every token issued before.

## What changed

- **Tokens.** ES256, signed with a P-256 key the hub makes when it signs its
  first token and stores encrypted with the encryption key. Claims: `iss`,
  `aud`, `sub` (the tenant's slug), `jti` (the key's ID), `cid` (its client
  ID), `iat`, `exp`. No budget or limit. They last
  `tokens.lifetimeDays`, 180 by default.
- **The gateways check them themselves**, from the public keys every sync
  writes into the SecurityPolicy inline: no cluster calls the hub, and tokens
  work while the hub is down. They read a token from `Authorization: Bearer`
  or from `x-api-key`, and set `x-aigw-tenant` from `sub` and `x-aigw-key`
  from `jti`, replacing what a client sent.
- **Revoking a token** refuses its `jti` on every gateway after the next
  sync, until it expires; deleting a tenant does the same for its tokens,
  and a disabled tenant is refused by its slug.
- **Rotate signing key** on the Tenants page: a new key signs from then on;
  the old one stays published while a token it signed is valid.
- **The Tenants page** says what the gateways take now, marks the tenants
  that still have API keys, shows each key's kind and a token's expiry, and
  **Create token** shows the token once with its expiry.
- **The tenants' own page** takes a token, checked on the hub.
- **The self-test** also sends a token signed by another key and an expired
  one, and, once the hub issues tokens, revokes a second token of its tenant
  and waits until the gateway refuses it.
- **Settings:** `tokens.issuer`, `tokens.audience`, `tokens.lifetimeDays`.
- **API:** `POST /tenants/{id}/keys` makes a token (`"kind": "key"` makes an
  API key); a key has `kind` and `expires_at`; `GET /signing-keys`, `POST
  /signing-keys/rotate`; a tenant has `api_key_count`.

## Tested

- **On the lab's real gateway first** (lab check C, Envoy Gateway 1.9.2, AI
  Gateway 1.2.0, on a listener of its own with a mock model that echoes the
  identity headers), with tokens signed the way the hub signs them:
  - accepted from `Authorization: Bearer` and from `x-api-key`;
  - `x-aigw-tenant` and `x-aigw-key` set from `sub` and `jti`, and a
    client's own `x-aigw-tenant` replaced, sent once or twice, with a token
    and with an API key;
  - another key's token and an expired token refused (401), a revoked `jti`
    (403);
  - the switch: API key and listed token in either header taken, an
    unlisted token refused (401), an expired listed token refused (403) by
    the rule on the credential's shape, a revoked one (403);
  - `AIServiceBackend.headerMutation` removing `Authorization` and
    `x-api-key` before the model.
- **Units:** signing and checking (forged, tampered, expired, unknown key,
  another hub or fleet, an API key); a key stored and read back; the JWKS
  checks a token. The policy of each mode: API keys only unchanged; both
  with `sanitize: false`, `failOpen`, the four rules in order, the claims,
  the backends removing the credentials; tokens only with no Secret, no API
  key check and `cid` to `x-aigw-client-id`; more than 128 revoked tokens
  split over rules.
- **Store, on Postgres:** the first token makes the signing key and the
  second reuses it; a token checks out against the published keys and names
  its tenant; the modes (keys, both while an API key is left, tokens); every
  key and token listed during the switch, an expired one not; a revoked
  token denied, a deleted tenant's tokens denied and kept, a disabled
  tenant by its slug, a denial dropped once its token expired; rotation keeps
  the old key published while its token is valid and drops it after.
- **The real CRDs** (`hack/test-apiserver.sh`), at Envoy Gateway 1.9.2 with
  AI Gateway 1.2.0 and at 1.9.1 with 1.1.0: both policies, 130 revoked
  tokens over two rules, the CEL rule and the backends' header mutation are
  accepted; moving to tokens only removes the Secret.
- **The hub renders it:** a local hub with an API key and three tokens, one
  revoked, rendered the switch policy for the lab's cluster with the revoked
  token left out of the Secret and denied by its `jti`.
- **The tenants' own page** on that hub: a token and an API key signed in;
  a revoked token and one signed by another key were refused (401).
- **The Tenants page** on that hub, at 1440 and 390 px: the panel said the
  gateways take both and named the tenant still on API keys; the key table
  showed kinds, a token's end and expiry, and the revoked token; no console
  errors, no overflow.
- Settings and their limits; the UI builds and type-checks.

## Not tested

- **The policy the hub renders, on the lab's real gateway.** The lab login
  expired before it was applied; the same policy, written by hand, is what
  lab check C tested. The self-test's new steps have not run against a real
  gateway for the same reason.
- **Many tokens.** The Secret during the switch and the deny list were
  tested with a handful of keys and 130 denials, not hundreds of tenants.
- **Rotation on a real gateway**: two keys in the key set were not sent to
  the lab.
- **A route of the cluster's own** passes the token on to the model server:
  not changed, and not tested.
