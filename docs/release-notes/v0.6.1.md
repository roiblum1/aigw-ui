# 0.6.1 (2026-10-09)

**Security fix. Upgrade if "Enforce API keys" is on for any cluster.**

## The problem

In every version up to 0.6.0, a key that was revoked kept working. So did
every key of a tenant that was disabled or deleted. The UI and the API showed
the key as revoked, and the task in Activity said the Secret was updated, but
the key was still in the Secret `aigw-ui-api-keys` on the clusters, and the
gateway accepts every key in that Secret.

The cause: the keys were written through the Secret's `stringData` field. The
API server copies `stringData` into `data`, but server-side apply only records
ownership of the `stringData` entries. An entry left out of a later apply was
therefore never removed from `data`.

Thanks to the external review that found this and reproduced it on a real API
server.

## The fix

- Keys are written under `data`, where server-side apply removes an entry
  that is no longer applied.
- After applying the Secret, each sync compares it with the keys it should
  hold and removes any other entry. This is what cleans up Secrets written by
  older versions, where the old entries have no owner and no apply can remove
  them.

## Upgrade

```sh
helm upgrade aigw-ui deploy/chart/aigw-ui -n aigw-ui
```

No migration. The first sync of each cluster after the upgrade removes the
stale keys. That happens by itself within `config.syncInterval` (5 minutes),
or at once with **Sync all**. With `config.autoSync` off, press **Sync all**.

Check one cluster afterwards. The Secret must list exactly the active keys of
enabled tenants:

```sh
oc get secret aigw-ui-api-keys -n <gateway namespace> -o go-template='{{range $k, $v := .data}}{{$k}}{{"\n"}}{{end}}'
```

**Treat keys revoked before this upgrade as having been usable until now.**
If a key was revoked because it leaked, look at the gateway's access logs for
its client ID (`<tenant>.<8 hex digits>`, shown on the tenant's page) over
that period.

The Manifests preview now shows the Secret's entries under `data` instead of
`stringData`, masked as before.

## What was tested

- Reproduced on a Kubernetes 1.37 API server: with the old code, the Secret
  still held all three keys after two were revoked.
- With the fix on the same server: the Secret held only the active key, both
  for a Secret created by this version and for one written the old way. A
  sync that changes nothing reports no change.
- These two tests are in the repository
  (`internal/kube/apiserver_test.go`). They need a real API server and are
  skipped without one:

  ```sh
  KUBE_TEST_KUBECONFIG=/path/to/kubeconfig go test ./internal/kube/ -run RealAPIServer
  ```

Not tested: that Envoy Gateway stops accepting a key as soon as it leaves the
Secret. It reads the Secret's `data`, so it should; the self-test's "unknown
key is refused" step does not cover a key that was once valid.
