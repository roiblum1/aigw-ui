# 0.36.0 (2026-10-25)

The Deployments page checks the vLLM command before it commits. KServe
hands the flags to vLLM unread: a flag vLLM does not have, a value it
refuses or a combination it stops on shows only when the pod starts,
minutes after Argo CD synced, and a flag set twice is taken from the last
place without a word. The hub now builds the command the pods will run and
reads it as vLLM 0.32.0 reads it, from a list written by vLLM's own parser.

Database: no migration.

## In short

**What was missing.** A misspelt flag (`--enable-prefix-cache`) went into
git, Argo CD synced it, and the pod crashed at start. A cluster's flag in
its own file that the recipe also set did nothing, because the recipe's
list comes later and vLLM takes the last. A shape that asked for 4 GPUs for
8 data-parallel ranks failed on the node.

**What 0.36.0 does.**

1. **The command, word by word.** The hub builds what KServe's launcher and
   the model-deployer chart pass to vLLM (`/mnt/models`, the served names,
   `--port 8000`, the parallel flags of `parallelism` or of data parallel
   over ports, the cluster's flags, the recipe's, the length, LMCache's
   connector), and for multi-node the leader's and the workers'.
2. **Read as vLLM reads it.** Against the flags of the image's vLLM
   version: vLLM's own rewriting (underscores, `-O3`, dotted keys) and
   argparse's rules (unique abbreviations, each value's type and choices,
   the keys of a JSON config), then the checks vLLM runs before it loads a
   model (serve checks, data parallel over ports, parallel and scheduler
   configs, `--speculative-config`'s keys).
3. **The hub's own rules.** A flag set twice, a flag KServe or the chart
   sets already, the GPUs a pod asks for against tensor × ranks, and
   warnings when the flags the prices need are off.
4. **On the page and in the API.** The form shows the findings and the
   whole command as it changes; a save with an error is refused; a recipe
   edit is checked on every cluster that runs the model; each deployment
   shows its check in short, files edited by hand in git included.

The flag list is vLLM 0.32.0's. An image tagged with another version, an
LMCache build (its tag is LMCache's version) or an empty `images.vllm` is
checked against it as warnings only. `hack/vllm-flags.sh <image>` writes the
list of another version.

## Upgrading

Nothing to do. A save that 0.35.0 committed may now be refused when its
image is `vllm*:v0.32.0` and the command would not start; the message says
which flag and where it came from.

## Added

- `POST /api/v1/gitops/check`; every Deployments save runs the same check
  and answers 400 with `checks` on an error; `flags` on each deployment of
  `GET /api/v1/gitops`.
- Package `internal/vllmflags` with the vLLM 0.32.0 flag list
  (`catalogs/vllm-0.32.0.json`) and vLLM's verdicts on 72 argument lists
  (`testdata/`); `internal/gitops/launch.go` (the command, the hub's rules).
- `hack/vllm-flags.sh` and `hack/vllm-flags.py`: a vLLM version's flag list
  and verdicts, written inside its image.
- The form's "vLLM check" section; the flag badge on each deployment.
