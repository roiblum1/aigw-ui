# 0.35.0 (not released yet)

The hub deploys the models too. A new page, Deployments, reads and writes
the values files of the Argo CD platform (argocd-day2-platform's layout:
`operators/<model>/` and `sites/<site>/<env>/mces/<mce>/<cluster>/<model>/`),
and Argo CD deploys them with one chart for every model, `model-deployer`
(in the doomsday-stack repository).

Database: no migration. The repository is the source of truth; the hub
keeps nothing of it.

## In short

**What was missing.** A model reached the hub only after someone deployed
it by hand: its own chart per model (glm53, qwen38, the judge), its values
in git, an Argo CD app, and then discovery found it. Running the same model
on another cluster in another shape (B300 with 8 data-parallel ranks, H200
with tensor parallel 8, two H200 nodes over RoCE) meant a values file
written by hand for each, with every flag repeated.

**What 0.35.0 does.**

1. **One chart for every model.** `model-deployer` is the whole stack the
   per-model charts deployed (node preparation, local PVs, per-node S3 pull
   jobs, the LMCache engine, the LLMInferenceService and its scheduler) plus
   the fleet side (the peer route, the health route, the request classes,
   flow control). glm53, qwen38 and the judge point at it; their recipes
   render what their old charts rendered, with three request classes and
   the capacity annotation added.
2. **A recipe per model, a shape per cluster.** The model's recipe
   (`operators/<model>/values.yaml`) holds what is the model's: weights,
   images, its vLLM and LMCache flags. Each cluster's own file holds its
   shape: data parallel over ports, tensor parallel, or a replica over two
   nodes on RoCE (KServe's LeaderWorkerSet), its GPUs and its own flags.
3. **The page.** Deploy a model on a cluster, change a cluster's values,
   remove a model from a cluster, edit a recipe, add a model copied from
   another. Each save is one commit; the hub writes only what differs from
   the layers below, and keeps the comments of the files it changes. Each
   deployment shows Argo CD's sync and health and how many of its replicas
   are ready.

## Upgrading

- The image has `git` and `ssh` (the hub commits with them). Nothing to do
  for a hub that does not use the page.
- To turn the page on: `gitops.repo`, `gitops.branch`, `gitops.dir`
  (`gitops/app-of-apps` for the platform's layout), and a Secret that may
  push (`gitops.existingSecret`, `gitops.auth: token` or `ssh`). See the
  deployment guide, "Before the first model deployment".
- Optional: `gitops.argocdNamespace` and the read-only Role in Argo CD's
  namespace, for each deployment's sync and health. The pod then mounts
  its account's token (it did not before).
- The doomsday-stack repository: merge `model-deployer` and point the model
  apps at the chart (their `operators/<model>/<model>.yaml`). The first sync
  of each model app changes its pods once where its recipe differs from its
  old chart (the request classes are new; the node-prep script's comments
  changed, which rolls the node-prep pods).

  `gitops.*`.
