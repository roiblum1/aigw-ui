# 0.13.0 (not released yet)

A **Capacity** page: measure what one instance of each shape of a model
serves at the latency you promise, and see what the model can be given a
day, how much of that the tenants' budgets take, and the one set of prices
that pays for its GPUs. See [capacity](../capacity.md).

## Shapes

- One model can run in several shapes at once: one node of 8× B300, one of
  8× H200, prefill and decode pods over several nodes. Discovery now reads
  every deployment's shape: its GPU from the node label
  `nvidia.com/gpu.product`, its GPUs per instance from what the pods ask
  for, and its topology.
- A measurement counts for every deployment of the same model and shape.
  A shape that is not measured is listed and not counted.
- Prefill and decode is not measured yet.

## Measuring an instance

- **Measure** on a shape starts AIPerf in a Job on the cluster, aimed at a
  ready pod of that shape that you choose, past the gateway and the
  scheduler. The form asks you to confirm that the pod's users get slower
  answers meanwhile.
- It replays made-up coding-agent sessions whose prompts average about
  100,000 tokens, with a shared system prompt, repository files and a
  growing history, at 1, 2, 4 … requests in flight. A step sends at least
  60 requests, so its 95th percentile rests on enough of them. It stops at
  the first step that misses the targets for the time to first token or
  between tokens.
- The Job prints one line of numbers per step. The hub reads them from the
  pod's log, so a measurement goes on while the hub restarts. Nothing of a
  prompt reaches the hub, and no tenant is charged.

## What a model can be given

For each model the page shows:

- each shape: ready instances, requests in flight within the targets, what
  one instance serves a day, its cost an hour and its cost per million
  tokens, which shows the hardware that serves the model for the least;
- what the model can be given a day: what the measured instances serve busy
  all day × the model's expected busy share;
- the tenants' daily budgets on it and the overcommit, and how far the
  budgets could go if tenants use them as on the busiest day. Quotas per
  minute or hour are limits on a rate and are not added;
- the busiest day and the average day of the last 30;
- with the GPUs priced, what the measured instances cost an hour and the one
  set of prices that pays for them at the expected busy share.

## Setting it up

- **GPU prices** on the page: what each GPU costs an hour, all in.
- **Expected busy share** per model, 60% until changed.
- New chart value `capacity.image`: an AIPerf image the LLM clusters can
  pull. Empty turns measurements off. `deploy/aiperf/Containerfile` builds
  one with AIPerf 0.13.0 and its tokenizer inside, and the offline bundle
  now carries it; `load-images.sh` prints the value to set.
- The hub needs, in each measured model's namespace, to create and delete
  Jobs and read pods and their logs, and across the cluster to read pods and
  nodes. See [security](../security.md).
- A database migration adds the deployments and their shapes, the GPU
  prices, the measurements and each model's expected busy share.

## Tested

- The arithmetic of shapes, costs and prices, the choice of the result step,
  the Job and the reading of its log, by unit tests.
- The Job's script with the real AIPerf 0.13.0, in the image the chart's
  `capacity.image` is built from, against a stand-in for vLLM with no
  network, in CI. Its first run found two faults that are now fixed:
  AIPerf read a scaled-down session's blocks as 512 tokens, and it held a
  request slot through the pause between turns.
- The following of a Job to each way it can end, against a stand-in cluster.
- Reading a deployment's shape, choosing its pod, and creating, reading and
  deleting the Job, against a real Kubernetes API server.
- The new queries against Postgres.
- Not run on a cluster or a GPU. Real figures need one.
