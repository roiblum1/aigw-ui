# 0.38.0 (not released yet)

The vLLM check on the Deployments page is now `vllm serve --help` and no
more. The hub keeps each vLLM version's flags as that version's own help
text, and checks a command's flags against it. It no longer imitates
vLLM's value types, JSON config keys and start-up checks, so a pod can
still stop on those when it starts. `internal/vllmflags` is half its size,
and adding a vLLM version is one command with nothing to compare.

Database: no migration.

## Upgrading

- Nothing to do. A save that 0.37.0 refused for a value's type, a JSON
  config key or a combination of flags is now taken, and the pod stops on
  it when it starts; its log says why.
- To add a vLLM version, run `hack/vllm-flags.sh <image>`. It writes
  `internal/vllmflags/catalogs/vllm-<version>.txt`; there are no verdicts
  to write.

## Changed

- **The flag lists are vLLM's help.** `catalogs/vllm-<version>.txt` is
  `vllm serve --help=all` as the image prints it, after one line naming the
  image. vLLM 0.32.0's replaces 0.36.0's JSON list. `hack/vllm-flags.sh`
  runs `vllm --version` and `vllm serve --help=all` in the image, and
  `hack/vllm-flags.py` is gone.
- **What the check refuses is what the help rules out:**
  - a flag the help does not list, with the nearest one;
  - a flag without its value, or a value given to a switch;
  - a value outside the choices the help shows as `{a,b}`;
  - a word that no flag takes.

  The hub's own rules stay as they were: a flag set twice, KServe's own
  flags, the GPUs a pod asks for, `parallelism.data` as a multiple of
  `dataLocal`, and warnings for the two flags the prices need. The command
  is still read as vLLM reads it first: underscores, `-O3`, dotted keys,
  `--flag=value`, and abbreviations, which get a warning.
- **Left to the pod's start:**
  - value types (`--max-num-seqs many`) and JSON that does not parse;
  - the keys of a JSON config (`--speculative-config` `{"methd": ...}`);
  - vLLM's serve checks (`--enable-auto-tool-choice` without
    `--tool-call-parser`);
  - the data-parallel launch checks;
  - `ParallelConfig` (EPLB without expert parallel);
  - `SchedulerConfig` (batched tokens below the length with chunked
    prefill off);
  - `--model` beside KServe's model.
- The page says "vLLM knows every flag" where it said "vLLM takes it".
- `internal/vllmflags` went from 1,394 lines of Go to 695. The test of 72
  commands against vLLM's verdicts is gone, with its data.

## Tested

On 2026-10-31, on macOS:

- `hack/vllm-flags.sh docker.io/vllm/vllm-openai-cpu:v0.32.0` (podman, no
  network). It found vLLM `0.32.0+cpu`, and the list matches a run of
  `vllm serve --help=all` by hand byte for byte. It has 316 flags, and every
  one of 0.36.0's 428 spellings is among them.
- Before the old verdicts were removed, the new check ran against them:
  vLLM 0.32.0's own answers on 72 commands, written in that image for
  0.36.0.
  - It took all 26 commands vLLM takes.
  - It refused 11 of the 46 vLLM refuses: 11 of the 18 refused while vLLM
    reads its flags, and none of the 28 refused by the serve checks, the
    engine's config checks or at start.
  - The 7 it misses while vLLM reads its flags: an integer, a float, a
    binary suffix with a decimal, JSON that does not parse, a config key
    with a bad choice, an unknown LMCache connector key, and the model
    given as `--model`.
- `go test -race ./...` with Postgres 17: 368 tests. They
  cover each shape of help line, commands vLLM takes, what the help rules
  out, and the Deployments check's cases, which are unchanged from 0.36.0.
- `go vet`, `gofmt`, `hack/check-duplication.sh`, the web tests (30), `tsc`
  and the build.

Not run:

- The page on a live hub.
- Live check 36. Its step 3's combination is no longer refused.
