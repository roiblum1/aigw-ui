# 0.30.0 (not released yet)

A tenant's own page shows its workload: requests, input, cached and output
tokens per model and hour as the gateways count them, the share of the
prompt read from the cache and what that saved. The hourly history follows
every counter by its own name and no longer falls short when a rule moves,
an old token counts under its former amount, or a reset follows a request.
Fixes and findings of the second end-to-end run of 0.29.0.

Database: migration 033 adds `usage_counter_cursors`, a cursor per Redis
counter the history reads, and `token_hours`, the requests and tokens of
each tenant on each model per hour. `usage_cursors` is read once by the
first look after the upgrade and then left empty.

## Upgrading

- With `redis.tokenCounts` on (the default), a Redis URL and tenants on
  tokens, the first sync writes four more rules into
  `aigw-ui-tenant-budgets`, and the policy is there without any budget too.
  They need Envoy Gateway's global rate limiting, as budgets across models
  do: on a cluster without it, set `redis.tokenCounts: false` first, or the
  policy is not accepted. The budget rule stays first: no budget counter is
  renamed.
- The routes the hub renders, and the routes of a cluster's own it marks,
  get three more `llmRequestCosts` keys (`aigw_ui_input`, `aigw_ui_cached`,
  `aigw_ui_output`). A route of the cluster's own that the hub does not
  touch counts requests but no tokens until the gateway's `GatewayConfig`
  declares the keys; see [deployment](../deployment.md#token-counts-on-every-route).
- The token history starts at the upgrade. The first look after it starts
  from the cursors of 0.29.0; a window that ends between the last look
  before the upgrade and the first after it loses what it counted after
  that last look, at most a minute of use.
- Going back to 0.29.0 finds `usage_cursors` empty: its first look adds the
  running window of every quota once more.
- The chart's memory limit is 1Gi (it was 512Mi) and its request 128Mi
  (64Mi). The chart passes the limit to the server as `MEMORY_LIMIT`, and
  the server keeps its heap to 90% of it; a `GOMEMLIMIT` set in the pod
  wins. A release that sets its own `resources` keeps them: raise its limit
  too.
- For one tenant's backlog not to hold up the others, a site's scheduler
  needs `round-robin-fairness-policy` on the band of priority 0; the sync
  now warns where it is missing. See
  [optimization](../optimization.md#tenants-in-turn).

## Added

- **The tenant's workload** on `/my-usage`: requests, prompt and output
  tokens, the share of the prompt from the cache, prompt and output tokens
  per request, what the cache saved at the model's prices; tokens (new
  input, cached input, output), the cache's share and requests per day for
  30 days or per hour for 2 days; the same per model. A model whose answers
  report no token counts, or that served nothing from its cache, is named
  with what to do. Numbers only: no prompt or answer reaches the hub.
  `GET /my/usage` has `token_counts`, `token_days` and `token_hours`.
- **Token counts** at the gateways: four rules of the budget policy on the
  client listener, one counter per tenant, model and hour each, in shadow
  mode with the largest limit. The chart value `redis.tokenCounts` (env
  `REDIS_TOKEN_COUNTS`) turns them off.
- **Self-test step** "The tenant's requests and tokens are counted by
  model": it reads the temporary tenant's token counters under the names the
  hub computes, and tells a route without the token keys from a missing
  counter.
- **A warning for tenants served oldest first.** On a pool of a best-effort
  model whose scheduler runs flow control, the sync warns when the band of
  priority 0 has no `round-robin-fairness-policy`: llm-d router v0.10.0's
  default, `global-strict-fairness-policy`, serves the oldest request
  first, whatever its fairness ID.

## Fixed

- **The hub ran out of memory with many tenants.** The end-to-end run of
  0.30.0 with 1,000 tenants saw the hub killed at its 512 MiB limit, at
  about 870 MiB (0.29.0: 45 MiB). To read a tenant whose limits changed
  under the model's other amounts, the history took every tenant's counter
  in turn and made the same keys once for each tenant that held the
  amount: 425,000 a minute, 850,000 with the model in best-effort mode
  (a second route to count on), of which about 8,500 differed. It now takes
  each amount's rule once, on each route and for every cluster together.
- **The hourly history fell short.** It kept one cursor per tenant and
  model and read only the counter names of the current rules. A counter
  whose rule moved within its window (a budget tenant's, after a new amount
  on the model) was never read to its end: 99 recorded against 147 counted.
  A token with the tenant's former amount counts under that amount's rule,
  which was not read at all. And a reset took away what was counted since
  the last look. The history now keeps a cursor per Redis key, reads a key
  it no longer computes to the end of its window, reads a tenant's other
  amounts while a token signed before its last change of limits may be in
  use, and a reset records the use since the last look first.
- **A model deleted by hand came back.** Discovery added a model the
  gateway still listed in the seconds after the hub removed its route (13 s
  on the lab), as a discovered model with no endpoint. A name only the
  gateway's model list has now updates a model the hub has and adds none.
- **Reading many counters.** Counters are read in batches of 1,000 keys
  per `MGET`, in one round trip.

## Changed

- **Documentation.** The pool's counter starts over when a new amount or
  the first budget across models changes its number of rules (78 credits
  through a pool of 20 on the lab); the best-effort limit needs the hub
  running, quotas, budgets and lists do not; a revoke reaches the gateways
  with the next sync, after one already running; flow control as seen on the
  lab; tenants in turn at a site; token counts on routes the hub does not
  touch.

On 2026-10-17, after the merge, an end-to-end run with 1,000 tenants (the
`/release-e2e` procedure) on the sandbox hub, image `sha-d376a65203c7`
(chart 0.30.0), and the lab: Envoy Gateway v1.9.2, Envoy AI Gateway
v1.2.0-patched.2, vLLM v0.29.0 on CPU, one replica, flow control on with
the default fairness. Tenants `e2e-r030b-*` (1,000, plus 16 for single
checks), `e2e-alias` and one throwaway model, all of it removed afterwards.

**Failed: the hub runs out of memory with 1,000 tenants.** It used 395 to
496 MiB a minute after seeding against its limit of 512 MiB, and was killed
(exit 137, `OOMKilled`) at 11:22 UTC, a minute after `qwen-tiny` went into
best-effort mode. It was then killed during the first history look after
each start (`CrashLoopBackOff`, 3 restarts in 2 minutes). With the limit
raised to 2 GiB for the rest of the run it peaked at 868 MiB a look; 0.29.0
used 45 MiB with the same tenants. With the tenants deleted it used 35 MiB.
[INFERENCE, from the code at `d376a65`] `formerAmounts`
(`internal/usage/history.go`) makes one counter for every tenant amount
counter on a model times every tenant whose limits changed within a token's
lifetime (180 days): about 500 × 850 = 425,000 keys a minute here, twice
that while the model has its best-effort route, of which some 8,500 are
different. Every tenant seeded or given limits in the last 180 days counts,
so a fleet of this size crash-loops on the upgrade. Fixed in code after the
run (below).

Scale (with the 2 GiB limit):

- Creating the 1,000 tenants took 138.8 s (0.29.0: 132 s).
- Three full syncs took 10.8 s each (13.0 s).
- `GET /tenants` took 1.40 s for 300 KB (1.21 s); `GET /usage` 2.89 s for
  883 KB (1.62 s). Postgres used 124 MiB after seeding (63 MiB).
- `aigw-ui-tenant-budgets` has 5 rules (2,238 bytes). A `max_tokens: 1`
  request took 0.90 to 1.60 s before seeding and 0.94 to 1.47 s after
  (0.29.0: 0.97 to 2.31 s): the four token rules add nothing that a CPU
  site shows.
- A revoked personal key's token was refused 9.8 s after the revoke.

What held:

- **Token counts.** The policy was Accepted with the budget rule first and
  four shadow rules; every route the hub renders or marks carries the three
  token keys. For a tenant with room, three answers, a 2,315-token prompt
  twice (2,304 cached the second time), one streamed answer on `qwen-tiny`
  and one answer on `e2e-alias` counted exactly: 6 requests, 4,768 input,
  2,304 cached and 40 output tokens; 1 request, 32 and 8. A request refused
  by the model list (403) counted nothing. `/my/usage` showed the same
  numbers for the hour once the history had looked (one minute). Forged
  `x-aigw-tenant` headers were counted for the sender. The self-test's new
  step passed before and after the run.
- **The history follows every counter by name.** A quota reset 18 s after
  three requests kept the three in the hour's row. Three tenants with
  counters under two amounts in the hour (3 and 33; 6 and 14) had one row
  each equal to the sum. Fourteen budget tenants' rows equalled their
  counters, among them two whose rule moved twice in the day (rules 10 and
  12; 9 and 10).
- **A model deleted by hand stays deleted.** The gateway listed it for
  13.9 s after the delete; it never came back in 3 minutes.
- **The warning for tenants served oldest first** appeared on the first
  sync after `qwen-tiny` went into best-effort mode and on none before.
  With that scheduler, one tenant's single request again waited behind
  another's six (31.7 and 26.0 s), as the warning says.
- Everything the 0.29.0 runs checked: quotas, budgets, lists, the pool,
  limits in tokens, best-effort (listed 0.6 s after reaching 6 of 6, moved
  16 s later; capped with no overshoot), best-effort below regular tenants,
  the cost formula (10 of 10), cached prices on both paths (288 credits
  instead of 2,592; Anthropic 292), the entry route, the retry patch, the
  drain refusal, the scheduler at 0 (500, answered 7 s after it was back), a
  live measurement (best step at 4 in flight) and the planner's figures, the
  planner's split on a local hub, spoofing, the hub at 0 for 70 s, backend
  headers.
- **Live changes** (new checks): a change carried by the token held for the
  new token at the first request, 3.7 to 8.2 s after it, before its sync
  ended (11.3 s); a disable and enable took 8 to 9 s, a pool change 8 to
  9.5 s, a price change 13.6 to 28.8 s. A token from before a change keeps
  the old amount, budget and list. An `aigw-token` client renewing every
  30 s took the new budget 31.5 s after the change. A stream running when
  its tenant was disabled finished.
- **Cancelled requests** (new check): a stream cut after 8 tokens was
  charged what vLLM generated (76 credits: 36 prompt and 10 output tokens);
  one cut just before the usage chunk was charged in full (161); vLLM
  stopped within about 2 s each time, and Envoy logged one `DC` and no
  retry. After six cancels at random moments vLLM had nothing running and
  the next answers' first token came as fast as before; the scheduler
  dropped a cancelled queued request at once (`EvictedContextCancelled`).

Found:

- A request the gateway refuses (429, 503) counts as a request with no
  tokens, so the page's requests and tokens per request include refusals.
- The tenant's page and the history read only the models a tenant may call
  now: an hour's use of a model then taken off its list is not shown.
- Lowering an own quota from 14 to 6 after 8 were used let a new token use 6
  more on the new amount's counter while the old token used its last 6: 20
  in the hour. A budget's window change from 1h to 1d starts a new count.
- A request cut before its first token (prefill), or a request without
  streaming that the client gave up on after vLLM had generated 11 tokens,
  was charged nothing.
- The lab evicted the model's pod for low ephemeral storage at 11:59; it
  served again at 12:07. Requests in between got 503 after the scheduler's
  60 s queue limit. A site event, not the hub's.
- `docs/api.md` says `/my/usage` takes an API key; it takes a token too.
