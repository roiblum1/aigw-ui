# Upgrading a hub from 0.12.3 to 0.32.1

A runbook for an agent or an operator who upgrades a running aigw-ui hub
from chart 0.12.3 straight to 0.32.1. Read all of it before the first
command. It also holds for a later 0.32.x patch release; read that
release's note too.

The jump is one `helm upgrade`. Migrations 016 to 035 run in order when the
new server starts, so nothing has to be done between versions. What needs
care is the first sync: the new version renders the cluster objects a little
differently from 0.12.3. You control that sync: switch automatic sync off
for the upgrade, look at what the new version would write, sync one cluster,
check it, then the others.

**Do not stop on 0.32.0.** Its token policy is CEL that Envoy does not
build, and a proxy then takes none of the hub's changes
([v0.32.0](../release-notes/v0.32.0.md)). Go from 0.12.3 straight to 0.32.1.

## Rules for the agent

- Every step below that changes something is marked **(change)**. Do those
  only with the operator's yes for this upgrade, and only on the hub and the
  clusters named for it.
- Never delete objects on an LLM cluster by hand. Never touch Gateway API
  CRDs, the Envoy Gateway or AI Gateway installation, or `openshift-*`
  namespaces.
- Credentials (kubeconfigs, the admin token, database passwords) stay in
  environment variables or in the cluster. Do not write them to files in a
  repository, to logs or to the report.
- If a check fails, stop and report: what failed, the output, and the state
  the hub and the clusters are in. Do not work around it.
- Write the report with placeholders for hosts and cluster names if it
  leaves the operator's network.

## What you need

| Input | Example |
|---|---|
| The hub's namespace and Helm release | `aigw-ui` / `aigw-ui` |
| `oc` logged in to the hub's cluster, with rights on that namespace | |
| `oc` access to each LLM cluster, read-only is enough except for the checks you are allowed | |
| The admin token, from secret `aigw-ui-auth` key `admin-token` | `export ADMIN_TOKEN=$(oc get secret aigw-ui-auth -n aigw-ui -o jsonpath='{.data.admin-token}' \| base64 -d)` |
| The hub's URL | `export HUB=https://aigw-ui.apps.example.internal` |
| The repository at tag `v0.32.1` (for the chart) | `git checkout v0.32.1` |
| The image `ghcr.io/roiblum1/aigw-ui:0.32.1`, or its copy in the site's mirror when disconnected | |

API calls below are `curl -sf -H "Authorization: Bearer $ADMIN_TOKEN" $HUB/api/v1/...`.

## What changes from 0.12.3 to 0.32.1

Only what an upgrade from 0.12.3 meets. Features that start only when an
operator uses them (tokens, budgets across models, quotas by amount,
capacity measurements) change nothing at the upgrade. Each version's
`## Upgrading` section in `docs/release-notes/` has the details.

### The hub

| Area | Change | Since |
|---|---|---|
| Database | Migrations 016 to 035 run at the start, in one go. They add tables and columns; 024, 028 and 032 drop only columns that versions after 0.12.3 added. Going back means restoring the backup (see Rollback) | 0.13.0 to 0.32.0 |
| Memory | The chart's limit is 1Gi (was 512Mi), the request 128Mi (64Mi); the server keeps its heap to 90% of the limit (`MEMORY_LIMIT`). A release that sets its own `resources` keeps them: raise its limit to at least 1Gi. 0.30.0 used up to 868 MiB with 1,000 tenants, 0.32.1 183 MiB | 0.30.0 |
| CPU | The request is 250m (was 50m), still no limit | 0.31.0 |
| New values | `capacity.*` (empty image turns measurements off), `tokens.*` (issuer, audience, lifetimes), `redis.tokenCounts` (default `true`). The defaults are safe for an upgrade | 0.13.0, 0.18.0, 0.30.0 |
| Startup | The hub syncs every cluster as soon as it starts, when automatic sync is on | 0.32.0 |
| Cluster API | A sync sends up to 50 requests a second to each cluster's API server (was 5) | 0.31.0 |
| Image | About 57 MB larger: it carries the upstream projects' docs | 0.28.0 |
| API | `GET /usage/history` with a `tenant_id` that is not a UUID answers 404 | 0.31.0 |

### The clusters, at the first sync

- **AIServiceBackends** the hub renders remove the credentials
  (`Authorization`, `x-api-key`) and the request field `kv_transfer_params`
  before the model server (0.18.0, 0.29.0).
- **Entry routes** (`fleet-<slug>`) also retry a 500 from a site (0.29.0).
  On a cluster whose client listener serves plain HTTP every retry patch is
  written for both names of the route configuration.
- **Models added by hand** start to charge their tenants' quotas each
  answer's cost (0.29.0). What went uncounted before is not added.
- **QuotaPolicies** can have their rules in another order than 0.12.3 wrote.
  Positions are part of the Redis counter names, so a quota whose rule
  moved counts from 0 for the rest of its running window, once. Phase 3
  shows whether that happens.
- **Model servers' backends** past ten models with quotas by amount get
  their own policies (0.29.0); with API keys only there are no quotas by
  amount, so nothing changes there.
- **Token counts** (`aigw-ui-tenant-budgets`) are written only once a Redis
  URL is set, `redis.tokenCounts` is on and tenants are on tokens. A hub on
  API keys only writes nothing new.

### Gateway versions

The hub's objects are tested against Envoy Gateway v1.9.1 with Envoy AI
Gateway v1.1.0, and Envoy Gateway v1.9.2 with AI Gateway v1.2.0
(`hack/test-apiserver.sh`). Record the versions on each cluster in phase 1.
Two features need more, and both are off until used:

- a budget across models needs Envoy Gateway 1.9.0 or later and its global
  rate limiting with the shared Redis
  ([deployment](../deployment.md#before-the-first-budget-across-models));
- token counts on routes the hub does not render need AI Gateway 1.2.0's
  `GatewayConfig` ([deployment](../deployment.md#token-counts-on-every-route)).

Before the first tenant moves to tokens on a cluster without Envoy Gateway's
global rate limiting, set `redis.tokenCounts: false`, or the token-count
policy is not accepted there.

### Permissions the new version can use

Without them the hub works as before and says what it could not read.

- get and list on `llminferenceserviceconfigs.serving.kserve.io`,
  cluster-wide (0.16.0): without it a change in a shared config does not
  mark a capacity measurement stale;
- get on the `Deployment` or `LeaderWorkerSet` of each LLMInferenceService,
  its `InferencePool`, the `Gateway`, and the HTTPRoutes in the gateway
  namespace (0.29.0). Without get on HTTPRoutes every sync warns about the
  gateway chart's health check where it is on.

See [security](../security.md#kubeconfigs).

## Phase 1: look, change nothing

1. **Versions.** `helm list -n aigw-ui` shows chart `aigw-ui-0.12.3`.
   `curl $HUB/healthz` answers `ok`.
2. **Gateway versions** on each LLM cluster: the Envoy Gateway and AI
   Gateway controller images (`oc get deploy -n envoy-gateway-system -o
   wide`, and the AI gateway controller's namespace). Note them in the
   report.
3. **The hub's values:** `helm get values aigw-ui -n aigw-ui -o yaml > values-0.12.3.yaml`. Note
   `image.*`, `resources`, `redis.*`, `config.autoSync`,
   `config.syncInterval` and `global.imageRegistry`.
4. **Everything is in sync now.** `GET /api/v1/clusters`: every cluster has
   sync status `synced` and no pending change. Fix that before upgrading,
   or you cannot tell the upgrade's changes from older ones.
5. **Self-test baseline.** On each cluster: `POST
   /api/v1/clusters/{id}/selftest`, then poll `GET
   /api/v1/clusters/{id}/selftest` until it ends. Record every step's
   result. A step that already fails on 0.12.3 is not the upgrade's fault.
6. **The image is reachable.** Connected: check that
   `ghcr.io/roiblum1/aigw-ui:0.32.1` exists (`skopeo inspect
   docker://ghcr.io/roiblum1/aigw-ui:0.32.1`, or the package page on
   GitHub).
   Disconnected: the image must be in the mirror that
   `global.imageRegistry` names; copy it there first with the site's
   mirroring process.

## Phase 2: back up (change: files only)

1. The encryption key:
   `oc get secret aigw-ui-auth -n aigw-ui -o yaml > aigw-ui-auth.backup.yaml`.
   Keep it apart from the database dump. Without it the dump is useless.
2. The database, with the bundled Postgres:
   `oc exec -n aigw-ui aigw-ui-postgresql-0 -- pg_dump -U postgres -Fc aigw > aigw-0.12.3.dump`.
   With `externalDatabase`, the operator dumps it the same way. Check the
   file is not empty (`pg_restore -l aigw-0.12.3.dump | head`).
3. The objects the hub owns on each LLM cluster, for the comparison in
   phase 3:

   ```sh
   for kind in backends aiservicebackends aigatewayroutes backendtrafficpolicies \
       envoypatchpolicies httproutes inferenceobjectives quotapolicies securitypolicies; do
     oc get "$kind" -A -l app.kubernetes.io/managed-by=aigw-ui -o yaml > "before-<cluster>-$kind.yaml"
   done
   ```

   Do not export Secrets: they hold the API keys.
4. `helm history aigw-ui -n aigw-ui`: note the revision of 0.12.3, for a
   rollback.

## Phase 3: upgrade with automatic sync off

1. **(change)** Upgrade, with automatic sync off so no cluster changes yet:

   ```sh
   helm upgrade aigw-ui deploy/chart/aigw-ui -n aigw-ui \
     --reset-then-reuse-values \
     --set image.tag=0.32.1 \
     --set config.autoSync=false \
     --set resources.requests.cpu=250m,resources.requests.memory=128Mi,resources.limits.memory=1Gi \
     --wait --timeout 10m
   ```

   `--reset-then-reuse-values` (Helm 3.14 or later) takes the new chart's
   defaults and puts the release's own values on top. Do not use
   `--reuse-values`: it leaves out the values 0.12.3's chart did not have
   (`capacity`, `tokens`), and the templates fail on them. With an older
   Helm, pass the values saved in phase 1 instead (`-f
   values-0.12.3.yaml`) with the same `--set`s. Leave the `resources` line
   out if the release's own limit is already 1Gi or more.
2. **The pod starts.** `oc get pods -n aigw-ui`: `aigw-ui` ready, 0
   restarts, image `…/aigw-ui:0.32.1`
   (`oc get deploy aigw-ui -n aigw-ui -o jsonpath='{..image}'`). The
   Deployment has the new env vars `TOKEN_ISSUER`, `REDIS_TOKEN_COUNTS` and
   `MEMORY_LIMIT`, and `AUTO_SYNC` is `"false"`. `oc logs deploy/aigw-ui -n
   aigw-ui` has no `level=ERROR`. `curl $HUB/healthz` answers `ok`. The
   migrations ran:
   `oc exec -n aigw-ui aigw-ui-postgresql-0 -- psql -U postgres -d aigw -tAc "SELECT max(name) FROM schema_migrations"`
   prints `035_budget_pass_slot.sql`. A migration that fails stops the
   server before it listens, and the pod restarts: read its log.
3. **Nothing was written to the clusters.** `GET /api/v1/clusters`: the
   clusters may show pending; their last sync is still the one from before
   the upgrade.
4. **What 0.32.1 would write.** For each cluster:
   `GET /api/v1/clusters/{id}/manifests` returns the objects the next sync
   applies. Compare them with the `before-*` files from phase 2:
   - Expected: the AIServiceBackends' header and body removals, the entry
     routes' retry on 500, new annotations and `llmRequestCosts` entries.
   - **QuotaPolicies:** compare each policy's `bucketRules`, position by
     position. A rule of a tenant that sits at another index means that
     tenant's count starts again from 0 for its running window. Tell the
     operator which tenants and models; going on is their decision.
   - Stop and report anything else: an object that would disappear, a model
     whose route changes its backends, a weight of 0.

## Phase 4: one cluster first

1. **(change)** Pick the least busy cluster with the operator. `POST
   /api/v1/clusters/{id}/sync`. Then `GET /api/v1/tasks`: the task for that
   cluster succeeded; its message lists what changed. Note any warning in
   it.
2. **The gateway took it.**
   - The hub's view: `GET /api/v1/clusters` shows the cluster `synced`; no
     object `Rejected` or `Overridden` in the task.
   - The proxy's view: port-forward one Envoy proxy pod of the client
     gateway on port 19000 and read
     `/stats?filter=update_rejected`. Read it again after a second sync of
     the cluster: the counters must not grow. Its log must not have
     `failed to create an expression`.
3. **The self-test passes** on that cluster, with the same results as the
   baseline or better. Every new failure is a stopping point: report it with the
   step's message.
4. **Traffic.** Ask the operator to confirm that tenants on that cluster
   are answered (their own clients or a test key). The Usage page shows
   their requests counting.

## Phase 5: the other clusters

1. **(change)** Sync the other clusters one at a time (`POST
   /api/v1/clusters/{id}/sync`), each with phase 4's checks 1 to 3.
2. **(change)** Turn automatic sync back on to what it was:

   ```sh
   helm upgrade aigw-ui deploy/chart/aigw-ui -n aigw-ui --reset-then-reuse-values \
     --set config.autoSync=true --wait
   ```

   The hub syncs every cluster at the start. Check `GET /api/v1/tasks`: all
   succeeded.
3. Watch for an hour: `oc logs deploy/aigw-ui -n aigw-ui | grep -E 'level=(WARN|ERROR)'`,
   and `oc adm top pod -n aigw-ui` (memory well under the limit; 1,000
   tenants took 183 MiB).

## Rollback

Before any cluster was synced (phase 3): `helm rollback aigw-ui <0.12.3
revision> -n aigw-ui`, then restore the database (below), because 0.32.1's
migrations ran already.

After clusters were synced: the same. 0.12.3 then syncs the clusters back
to its own objects at its next sync. Use since the upgrade that the
history recorded is lost with the restore; the gateways' own counters in
Redis are not touched.

```sh
oc scale deploy/aigw-ui -n aigw-ui --replicas=0
oc exec -i -n aigw-ui aigw-ui-postgresql-0 -- pg_restore -U postgres -d aigw --clean --if-exists < aigw-0.12.3.dump
helm rollback aigw-ui <0.12.3 revision> -n aigw-ui --wait
```

The dump only works with the encryption key it was taken with: if
`aigw-ui-auth` changed, put back `aigw-ui-auth.backup.yaml` first.

## After the upgrade

Nothing more is required. The features since 0.12.3 start when an operator
uses them; each has its own steps:

- tokens instead of API keys, and personal keys that renew themselves
  (0.18.0, 0.23.0): [how it works](../how-it-works.md);
- budgets across models (0.22.0), which need Envoy Gateway's global rate
  limiting: [deployment](../deployment.md#before-the-first-budget-across-models);
- quotas by amount (0.24.0), which start when the last API key is revoked;
- capacity measurements (0.13.0, 0.16.0): set `capacity.image` to the
  AIPerf image built from `deploy/aiperf/Containerfile`, in a registry the
  LLM clusters reach ([capacity](../capacity.md));
- one tenant's backlog not holding up the others: `round-robin-fairness-policy`
  on each site's scheduler ([optimization](../optimization.md#tenants-in-turn));
  the sync warns where it is missing.

## The report

Write down, per phase: what was run, what it printed (without secrets), the
gateway versions, the self-test results before and after on every cluster,
the QuotaPolicy positions that moved and the tenants they concern, the
proxy's `update_rejected` counters, the hub's memory after an hour, and
anything that was not checked.
